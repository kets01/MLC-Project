=== MLC-Norm Sprint 2/2a: roofline validation + SSVE bandwidth ===

Byte convention: all GiB/s count USEFUL bytes = 1 read + 1 write per
element (the algorithm's minimum), for kernels AND probes alike.

MOVED bytes differ PER NORM, and the two must not be conflated:
  RMSNorm   1 reduction stage  (sum of squares) + output generation
            -> 2 input traversals, 2R+1W, moved = 1.5x the printed figure
  LayerNorm 2 reduction stages (mean, then variance) + output generation
            -> 3 input traversals, 3R+1W, moved = 2.0x the printed figure
The 1.33x traffic ratio between them is structural and is the main reason
RMSNorm outruns LayerNorm here.  (An earlier version of this header quoted
2R+1W without saying which norm, which reads as if it applied to both.)

SPRINT 7a - NUMERICAL STABILITY: where each variance formulation breaks
================================================================================================
Data: unit-variance samples shifted by s.  Variance is invariant under the
shift; the condition number kappa = 1 + mean^2/var is not.  All estimators
accumulate in FP32 (the kernels' precision); the oracle is float64.
Relative error vs the float64 oracle on identical input:

  shift          kappa  naive 1-pass      two-pass       Welford
  0e+00        1.0e+00      5.09e-07      3.89e-07      2.07e-07
  1e+01        2.0e+02      1.39e-04      3.98e-07      1.98e-07
  1e+02        2.0e+04      8.52e-03      1.18e-07      4.16e-07
  1e+03        2.0e+06      1.25e+00      3.75e-07      4.73e-06
  1e+04        2.0e+08      1.59e+02      2.81e-05      5.41e-05
  1e+05        2.0e+10      1.02e+04      1.51e-07      8.94e-05   <- naive NEGATIVE, sqrt = NaN
  1e+06        2.0e+12      6.80e+06      7.43e-07      6.71e-03   <- naive NEGATIVE, sqrt = NaN

Reading it: naive's error tracks kappa (each row multiplies the shift by 10,
hence kappa by ~100), and past shift 1e4 it returns a NEGATIVE variance -- so a
kernel built on it emits NaN, not merely an inaccurate number.  Two-pass is flat
across 12 orders of magnitude of kappa.  Welford sits between: vastly better
than naive, slightly worse than two-pass, and degrading slowly because its
running mean updates at full input magnitude (Sprint 6 §1.3).

Caveat stated rather than hidden: past shift ~1e5 the FP32 INPUT is itself
quantized (ULP of 1e6 is 0.0625, larger than the signal), so beyond that point
all estimators measure the variance of the quantized data.  They stay
comparable -- same input, same oracle -- but the 'true' variance drifts.

The shipped kernels on the same stress data (M=64, N=512), max|error| vs the
float64-accumulating C++ reference:

  shift      LN V0 (FSQRT) LN V6 (FRSQRTE)      LN Welford          RMS V6
  0e+00           7.15e-07        1.72e-05        1.72e-05        1.73e-05
  1e+01           1.13e-05        2.63e-05        2.65e-05        3.70e-06
  1e+02           1.30e-04        1.30e-04        1.02e-04        6.79e-06
  1e+03           4.63e-04        4.63e-04        8.47e-04        8.34e-07
  1e+04           5.37e-03        5.38e-03        2.16e-02        3.10e-06
  1e+05           1.23e-02        1.23e-02        2.14e-01        5.25e-06
  1e+06           2.07e-03        2.08e-03        3.02e-01        5.19e-06

Three readings, in order of how much they change the project's story:

1. The FRSQRTE cost is REAL BUT NARROW.  At shift 0, V0 (exact FSQRT+FDIV) is
   7.2e-7 against V6's 1.7e-5 -- a ~24x accuracy penalty for the ablation's
   winning variant, which Sprint 6 §1.3 found was never documented.  But from
   shift 1e2 upward the two are INDISTINGUISHABLE (1.30e-4 both).  So the
   substitution costs accuracy only where the problem is well conditioned; it
   is not what limits LayerNorm on hard data.

2. What DOES limit LayerNorm at high shift is not the variance at all.  Two-pass
   already fixed the variance (see the flat column above).  The residual error is
   in the OUTPUT expression (x - mean): when x ~ 1e5 and (x - mean) ~ 1, the FP32
   representation of x carries the difference in only a handful of bits.  At
   shift 1e5 the ULP near 1e5 is ~1.6e-2 relative to a unit signal, and the
   measured error is 1.2e-2 -- the two agree, so this is an INPUT-REPRESENTATION
   limit that no variance algorithm can remove.  That V0 and V6 coincide here is
   the evidence: the sqrt arithmetic is not the binding constraint.
   (The non-monotonic dip at 1e6 is the same effect seen from the other side --
   once the input is coarsely quantized, (x - mean) becomes exactly
   representable more often, so the kernel's own rounding falls.)

3. RMSNorm is flat at ~5e-6 across the whole sweep, ~2300x better than LayerNorm
   at shift 1e5.  This is context.md §8's claim confirmed on the shipped kernel:
   RMSNorm never forms a mean, so it never performs the cancelling subtraction --
   neither in the reduction nor in the output.  Its stability is structural, and
   it is the same property that makes it faster (2R+1W vs 3R+1W).  Accuracy and
   throughput point the same way here, which is unusual and worth saying.
   RMSNorm's own limit is elsewhere: Sum(x^2) overflows FP32 at |x| ~ sqrt(3.4e38/N).

SPRINT 7b - STREAMING-MODE OVERHEAD: what the transition actually costs
================================================================================================

Direct measurement (2000000 iterations, best-of-20).  The empty loop is
the control: identical branch structure and counter, transition removed, so
the difference is the transition rather than the loop.

  variant                           ns/iteration       minus control
  empty loop (control)                     0.226                   -
  smstart + smstop (SM+ZA)                 9.292               9.066
  smstart sm + smstop sm (SM only)         9.298               9.072

Two results here.  First, ONE round trip through streaming mode costs about 9.1 ns.
Second, SM+ZA and SM-only are the same to within noise (9.066 vs 9.072), so managing
PSTATE.ZA is free — the ZA kernels' problem was never the transition.

The per-call floor (RMSNorm V7 at its smallest possible call, M=1, N=1):

  measured floor                     :     57.4 ns/call
  of which the streaming transition  :      9.1 ns  (15.8 % of the floor)
  everything else                    :     48.3 ns

Note this is measured, not fitted. A linear fit over these sizes returns a
NEGATIVE intercept because the sweep crosses cache levels, so the model does
not hold — which is precisely how the inferred t0 went wrong before.

The transition is about a FIFTH of the floor — real, but not the thing that
makes a small call expensive. The other ~48 ns is prologue/epilogue (this project
saves d8-d15 on every call — the AAPCS64 fix from Sprints 5/6), pointer
setup, and the inv_rms serialization.

Worth comparing against the inferred figures this replaces: Sprint 2a read
t0 ~ 1000 ns from a fit and Sprint 4 corrected it to ~400 ns after removing a
syscall. The measured floor is 57 ns. Those are not the same quantity — the fits
were at M=128, which pays more setup than this M=1 minimum — but the gap is
large enough to say the intercept was never a clean read of fixed cost.

What the 'one streaming region per call' decision (context.md §8) is worth,
quantified: the alternative costs one transition per row. At M=128 that is
128 x 9.1 ns = 1.16 us/call against a single 9.1 ns — about 20x the entire
per-call floor. So the decision is right, and now it is right by a measured
margin rather than by assumption. But the constant itself is 9 ns: 'streaming
mode is expensive' is true per ROW and false per CALL, and only the second of
those is what this kernel does.

Crossover: at what size does the SME kernel beat the scalar reference?
(RMSNorm, N=512 — a realistic transformer feature dimension — sweeping rows)

  M rows       scalar us         V7 us     speedup  groups touched
  1                0.250         7.791        0.03x              1
  2                1.041         6.500        0.16x              1
  4                2.166         6.208        0.35x              1
  8                4.375         6.084        0.72x              1
  16               8.875         6.208        1.43x              1
  64              66.000         6.291       10.49x              1
  256            378.667        25.292       14.97x              4

The crossover is at M ~ 16 rows, and the reason is NOT streaming overhead.
Look at the last column: V7's time is flat from M=1 to M=64 because that is
ONE group. V6/V7 process 4 VL-row blocks at a time (VL=16 lanes at SVL=512,
so a group is 64 rows), and a partially-filled group costs the same as a full
one — the lanes are predicated off, not skipped. At M=1 the kernel does 64
rows' worth of work for 1 row's worth of result.

So the small-tensor penalty is GROUP GRANULARITY, not SMSTART. The fix would
be a narrower group for small M — which is exactly the shape-specialized
emission decision the JIT was built to make (Sprint 4) and which Sprint 2b
deferred. It is also the same granularity that made Sprint 6's threaded
chunking sensitive to alignment: chunks not a multiple of 64 rows pay this
same partial-group cost on every thread.
